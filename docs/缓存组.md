# 缓存组

## 1. 缓存组的定位

缓存组（`CacheGroup`）是分布式缓存中的逻辑抽象，表示一类具有相同数据含义、数据来源和缓存策略的 key-value 数据。

缓存组不是某一台物理服务器，也不是单独的 LRU 数据结构，而是一个缓存管理边界：

```text
CacheGroup
├── group_name：逻辑命名空间
├── local LRU：当前节点上的本地缓存
├── DataGetter：未命中时的数据来源
├── SingleFlight：合并相同 key 的并发加载
└── PeerPicker：可选的远程节点选择器
```

同一个逻辑缓存组可以同时存在于多个物理节点上：

```text
user_group@节点 A
user_group@节点 B
user_group@节点 C
```

这些同名实例共同组成分布式意义上的 `user_group`。

不同缓存组之间完全独立：

```text
user_group@节点 A
product_group@节点 A
order_group@节点 A
```

它们可以拥有不同的本地缓存、数据加载器、容量配置、统计信息和同步策略。

## 2. 为什么需要逻辑缓存组

缓存项的完整身份不是单独的 `key`，而是：

```text
(group_name, key)
```

例如：

```text
(user_group, 42)     // 用户 42
(product_group, 42)  // 商品 42
(order_group, 42)    // 订单 42
```

虽然它们的 key 都是 `42`，但语义、数据来源和缓存策略都不同。

缓存组可以提供以下隔离：

- **命名空间隔离**：不同业务的相同 key 不会互相覆盖；
- **数据来源隔离**：每个 group 绑定自己的 `DataGetter`；
- **缓存资源隔离**：不同 group 可以使用独立的 LRU 和容量；
- **并发控制隔离**：不同 group 使用独立的 `SingleFlight`；
- **同步策略隔离**：Set、Delete 和 Invalidate 只影响对应的 group。

如果所有数据都放进一个全局 LRU，就必须在每个 key 前手动拼接业务前缀，并且需要让一个 getter 处理所有业务数据。缓存组把这些边界显式地封装起来，便于管理。

## 3. 缓存组在读取链路中的位置

用户请求应该包含缓存组名称和 key：

```text
group_name = "user_group"
key        = "42"
```

请求到达某个缓存节点后，先根据 group name 找到该节点上的对应实例：

```text
请求(user_group, 42)
    ↓
当前节点的 groups["user_group"]
    ↓
user_group 的本地 LRU
```

在支持远程节点的完整版本中，读取链路是：

```text
当前节点的 CacheGroup
    ↓ 本地 LRU miss
PeerPicker / 一致性哈希
    ↓ 选择负责该 key 的节点
远程节点上同名的 CacheGroup
    ↓ 远程 LRU miss
DataGetter / 原始数据源
```

更具体地说：

```text
请求到达节点 A
    ↓
A 的 user_group 本地 LRU miss
    ↓
一致性哈希判断 key 属于节点 B
    ↓
A 请求 B 的 user_group
    ↓
B 的本地 LRU 命中，返回给 A
```

如果 B 也未命中，则由 B 的 `DataGetter` 回源。远程 RPC 必须携带 `group_name`，这样 B 才能访问自己的 `groups["user_group"]`，而不是访问其他缓存组。

远程节点处理 peer 请求时，应使用“只查本地并允许本地回源”的路径，不能再次完整执行 PeerPicker，否则可能形成递归请求：

```text
节点 A → 节点 B → 节点 C → 节点 A → ...
```

## 4. group name 与一致性哈希

缓存组隔离和节点路由是两个不同的问题：

```text
group_name
    决定使用哪一个逻辑缓存空间和加载策略

consistent hash
    决定这个缓存组中的 key 应该由哪个物理节点负责
```

### 4.1 只对 key 做哈希

参考实现使用类似下面的方式选择节点：

```cpp
PickPeer(key);
```

此时相同 key 在不同缓存组中可能映射到同一个节点：

```text
hash("42")

(user_group, 42)    → 节点 B
(product_group, 42) → 节点 B
```

这不是哈希冲突，因为节点 B 上仍然有两个独立的缓存空间：

```text
B.groups["user_group"].cache_["42"]
B.groups["product_group"].cache_["42"]
```

### 4.2 将 group name 加入哈希输入

也可以使用组合路由 key：

```cpp
hash(group_name + ":" + key);
```

这样不同缓存组中的相同 key 可能被分配到不同节点：

```text
(user_group, 42)    → 节点 B
(product_group, 42) → 节点 C
```

这种方式可以让不同 group 的数据分布相互独立，但它是路由策略的选择，并不是实现命名空间隔离的必要条件。

无论采用哪种方式，都必须保证：

- 所有节点使用相同的哈希函数和哈希环；
- 节点名称、虚拟节点命名和 group name 稳定；
- 组合字符串使用明确的分隔符或无歧义的编码；
- 需要在文档中明确路由 key 是 `key` 还是 `(group_name, key)`。

## 5. 缓存组与物理节点的关系

一个物理节点可以承载多个缓存组：

```text
节点 A
├── user_group
├── product_group
└── order_group
```

多个缓存组映射到同一个物理节点是正常的，不会造成数据覆盖。但这些 group 会共享节点的 CPU、内存、网络和线程资源，因此后续仍需要考虑节点级的总容量和负载管理。

可以用下面的关系理解整个系统：

```text
CacheGroup
    负责逻辑数据空间和缓存行为

ConsistentHashMap
    负责 key 到节点的路由

PeerPicker
    负责根据路由结果找到对应的 Peer

Peer / gRPC
    负责节点间通信

LRUCache
    负责节点内的实际缓存和淘汰
```

## 6. 当前项目的实现状态

当前 `KCacheGroup` 已经具备：

```text
命名缓存组
    → 本地 LRU
    → DataGetter
    → SingleFlight
```

因此当前实际链路是：

```text
KCacheGroup::Get
    → 本地 LRU
    → getter
```

当前代码还没有把 `ConsistentHashMap` 与 `KCacheGroup` 连接起来，也没有实现 `PeerPicker`、`Peer` 和 gRPC 远程访问。因此它目前是单节点本地缓存组的基础版本。

后续接入分布式能力时，可以将链路扩展为：

```text
KCacheGroup::Get
    → 本地 LRU
    → PeerPicker / 一致性哈希
    → 同名远程 CacheGroup
    → DataGetter
```

## 7. 核心结论

缓存组的核心意义是：

> 在逻辑上把不同业务、不同数据来源和不同缓存策略的数据分开管理；一致性哈希则独立负责把某个缓存组中的 key 分配到具体缓存节点。

`group_name` 是否加入哈希输入，可以作为路由策略单独选择：

- 不加入：相同 key 可能落到同一节点，但依靠 group namespace 保证数据隔离；
- 加入：不同 group 的相同 key 可以获得独立的节点分布。

无论采用哪种策略，缓存组的命名空间语义和一致性哈希的节点路由语义都应该保持解耦。
