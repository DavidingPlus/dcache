# 分布式缓存通信基础：从完整链路理解 Protobuf、gRPC 与 etcd

本文不从某个具体库或某个具体实现出发，而是从一条完整的分布式缓存通信链路出发，逐步解释：

- etcd Server 和 etcd Client；
- gRPC Server 和 gRPC Client；
- Protobuf、.proto 和 protoc；
- gRPC 服务基类、Stub 和运行时 Server；
- 服务注册、租约、Watch、节点路由和缓存请求之间的关系。

整篇笔记的主线是：

~~~text
启动基础设施
    ↓
缓存节点启动并注册自己
    ↓
路由组件发现节点
    ↓
根据 key 选择目标节点
    ↓
Protobuf 编码请求
    ↓
gRPC Client 发起远程调用
    ↓
HTTP/2 传输
    ↓
gRPC Server 接收调用
    ↓
Service 实现访问本地缓存
    ↓
Protobuf 编码响应并返回
~~~

沿着这条链路，可以自然理解每个组件的职责和位置。

---

## 1. 先建立整体图景

一个典型的分布式缓存系统同时包含两条链路。

### 1.1 控制链路：管理节点拓扑

控制链路解决：

~~~text
有哪些缓存节点？
每个节点的地址是什么？
某个节点是否还在线？
节点列表发生了什么变化？
~~~

这条链路通常使用 etcd：

~~~text
缓存节点内部的 etcd Client
            │
            │ 注册、续租、Get、Watch
            ▼
       etcd Server
            │
            │ 返回节点信息和变化事件
            ▼
本地节点列表、服务发现模块、一致性哈希环
~~~

### 1.2 数据链路：执行缓存操作

数据链路解决：

~~~text
某个 key 应该请求哪个节点？
如何向这个节点执行 Get、Set、Delete？
如何返回缓存结果？
~~~

这条链路通常使用一致性哈希、Protobuf 和 gRPC：

~~~text
业务请求
    ↓
一致性哈希选择节点
    ↓
gRPC Client
    ↓
Protobuf 序列化
    ↓
gRPC + HTTP/2
    ↓
目标节点的 gRPC Server
    ↓
Protobuf 反序列化
    ↓
Service 业务实现
    ↓
本地 CacheGroup / LRU
~~~

### 1.3 两条链路的边界

~~~text
etcd：告诉系统“节点在哪里”
一致性哈希：决定“应该选哪个节点”
Protobuf：定义和编码“请求数据是什么”
gRPC Client：发起“远程调用”
gRPC Server：接收“远程调用”
缓存业务：处理“本地数据”
~~~

通常，etcd 不参与每一次缓存 Get 和 Set。缓存请求走数据链路，etcd 主要维护控制链路。

## 2. 从启动到请求：完整链路拆解

下面按照时间顺序，观察一个缓存节点如何加入系统，以及一次 Get 请求如何完成。

### 2.1 第一步：启动 etcd Server

etcd Server 是独立运行的基础设施服务，可以是：

- 一个单独的 etcd 进程；
- 一个多节点 etcd 集群；
- Docker 或 Kubernetes 中的 etcd 实例。

它负责保存控制信息，例如：

~~~text
/services/cache/nodes/node-a
/services/cache/nodes/node-b
/services/cache/nodes/node-c
~~~

etcd Server 不是缓存节点，也不保存缓存系统中的全部 key-value 数据。

单节点开发环境中常见的端口是：

~~~text
2379：客户端访问端口，缓存节点的 etcd Client 通常连接这里
2380：etcd 成员之间的 Peer 通信端口
~~~

### 2.2 第二步：缓存节点启动 gRPC Server

每个缓存节点启动自己的 gRPC Server，监听缓存业务端口：

~~~text
Cache Node A：10.0.0.11:8001
Cache Node B：10.0.0.12:8001
~~~

这个端口负责接收缓存业务调用，例如：

~~~text
Get
Set
Delete
Invalidate
~~~

它和 etcd 的 2379 端口不是同一个服务。

### 2.3 第三步：缓存节点启动 etcd Client

缓存节点内部还需要一个 etcd Client。它连接 etcd Server，并向 etcd 注册自己的 gRPC 地址：

~~~text
Cache Node A
    └── etcd Client
            │
            │ Put / Lease / Watch
            ▼
        etcd Server:2379
~~~

节点注册信息可以约定为：

~~~text
key:
    /services/cache/nodes/node-a

value:
    grpc_address = 10.0.0.11:8001
~~~

这里的 etcd Client 负责控制平面，不负责执行缓存 Get。

### 2.4 第四步：创建 Lease 并续租

节点注册信息通常绑定一个 Lease：

~~~text
申请 Lease
    ↓
Put 节点信息并绑定 Lease
    ↓
KeepAlive 持续续租
~~~

节点在线时，持续发送 KeepAlive。节点崩溃或网络断开后，无法继续续租，Lease 过期，注册信息就会被删除或视为失效。

这样，节点不需要在崩溃前主动注销自己。

### 2.5 第五步：Watch 节点目录

客户端、网关或缓存节点可以 Watch：

~~~text
/services/cache/nodes/
~~~

当节点加入或离开时，etcd Server 推送事件：

~~~text
PUT    /services/cache/nodes/node-b
DELETE /services/cache/nodes/node-c
~~~

etcd Client 收到事件后更新本地节点列表：

~~~text
etcd Watch 事件
    ↓
本地节点注册表
    ↓
一致性哈希环
~~~

到这里，系统已经知道“有哪些节点”和“每个节点在哪里”。

### 2.6 第六步：根据 key 选择节点

当业务请求到来时，路由组件根据 key 计算节点：

~~~text
key = user:42
    ↓
一致性哈希
    ↓
目标节点 = Cache Node B
~~~

一致性哈希只负责节点选择，不负责：

- 建立网络连接；
- 序列化请求；
- 执行远程方法；
- 读取本地缓存。

### 2.7 第七步：gRPC Client 发起请求

选择节点后，调用方使用 gRPC Client 发起 RPC：

~~~text
gRPC Client
    │
    │ Get(Request)
    ▼
Cache Node B 的 gRPC Server
~~~

gRPC Client 一般由以下部分组成：

- Channel：目标节点的连接通道；
- Stub：生成的远程调用对象；
- Context：超时、取消和元数据；
- Request：请求消息；
- Response：响应消息。

### 2.8 第八步：Protobuf 编码请求

gRPC 调用发送前，需要把 Request 对象编码成二进制：

~~~text
Request 对象
    ↓
Protobuf Serialize
    ↓
二进制消息
~~~

Protobuf 负责：

- 定义消息字段；
- 生成消息类；
- 序列化；
- 反序列化；
- 提供字段访问和反射信息。

Protobuf 不负责：

- 查找目标节点；
- 建立连接；
- 监听端口；
- 调用远程函数。

### 2.9 第九步：gRPC 和 HTTP/2 传输

编码后的 Protobuf 二进制消息由 gRPC 负责传输。标准 gRPC 通常使用 HTTP/2：

~~~text
Protobuf 二进制消息
    ↓
gRPC 调用
    ↓
HTTP/2
    ↓
目标节点
~~~

gRPC 还负责处理：

- 方法名；
- 请求和响应；
- Status 状态；
- 超时；
- 取消；
- 元数据；
- 流式调用；
- 连接复用。

因此，更准确的说法是：

> gRPC 是一套 RPC 框架和通信机制，通常使用 HTTP/2 传输，并通常使用 Protobuf 编码消息。

### 2.10 第十步：gRPC Server 接收请求

目标节点的 gRPC Server 收到请求后：

~~~text
接收 HTTP/2 连接
    ↓
识别 gRPC 方法
    ↓
Protobuf 反序列化
    ↓
调用 Service 实现
    ↓
访问本地缓存
    ↓
构造 Response
    ↓
Protobuf 序列化
    ↓
返回 gRPC Status 和响应
~~~

本地业务路径通常是：

~~~text
gRPC Server
    ↓
生成的 Service 接口
    ↓
业务 Service 实现
    ↓
CacheGroupRegistry
    ↓
CacheGroup
    ↓
本地 LRU
~~~

### 2.11 第十一步：返回响应

响应返回到客户端后，处理过程与请求相反：

~~~text
本地缓存结果
    ↓
GetResponse 对象
    ↓
Protobuf Serialize
    ↓
gRPC + HTTP/2
    ↓
gRPC Client
    ↓
Protobuf Parse
    ↓
客户端 Response 对象
~~~

## 3. 同一个节点中各个角色的位置

一个缓存节点可能同时拥有多个通信角色：

~~~text
+------------------------------------------------------+
| Cache Node                                            |
|                                                      |
|  etcd Client                                         |
|      └── 连接 etcd Server，注册、续租、Watch          |
|                                                      |
|  gRPC Server                                         |
|      └── 接收其他组件对本节点的缓存调用               |
|                                                      |
|  gRPC Client                                         |
|      └── 调用其他缓存节点的 gRPC Server               |
|                                                      |
|  Route / PeerPicker                                  |
|      └── 根据节点列表和 key 选择目标节点              |
|                                                      |
|  CacheGroup / LRU                                    |
|      └── 执行本地缓存读写和淘汰                       |
+------------------------------------------------------+
~~~

对应的外部连接是：

~~~text
Cache Node 的 etcd Client
    ───────────────> etcd Server
                    控制平面

Cache Node A 的 gRPC Client
    ───────────────> Cache Node B 的 gRPC Server
                    数据平面
~~~

这就是为什么“一个缓存节点既可以是 gRPC Server，也可以是 gRPC Client”：它既接收别人请求，也可能请求别的节点。

## 4. etcd Server 和 etcd Client

### 4.1 etcd Server 的职责

etcd Server 负责保存和传播控制信息：

- 节点注册信息；
- Lease；
- Watch 状态；
- 服务发现数据；
- 集群配置；
- 少量需要强一致维护的元数据。

etcd Server 不负责：

- 缓存 LRU；
- 缓存 value 的高频读写；
- 一致性哈希；
- 缓存业务 RPC；
- 代替缓存节点执行 Get。

### 4.2 etcd Client 的职责

etcd Client 是应用程序内部的客户端库，负责调用 etcd Server 的 API：

~~~text
etcd Client
    ├── Put：注册节点
    ├── Get：读取节点列表
    ├── Lease：创建和续租
    ├── Watch：监听节点变化
    └── Delete：主动注销节点
~~~

它一般不会参与每一条缓存请求：

~~~text
错误方式：
    每次 Get
        ↓
    访问 etcd
        ↓
    再访问缓存节点

常见方式：
    etcd Client 定期更新本地节点列表
        ↓
    缓存请求直接使用本地路由
        ↓
    通过 gRPC 访问缓存节点
~~~

### 4.3 etcd Client 和 etcdctl

etcdctl 是命令行管理工具，适合：

- 手动查看 key；
- 写入测试数据；
- 查看 Lease；
- 检查节点健康状态。

它不是缓存程序中的业务 etcd Client。业务程序需要使用客户端库或自己的 API 封装。

## 5. gRPC Server 和 gRPC Client

### 5.1 gRPC Server 的职责

gRPC Server 是真正运行并监听端口的服务对象，负责：

- 接收网络连接；
- 接收 RPC；
- 解析请求；
- 调用 Service 实现；
- 返回响应和状态。

在缓存系统中，它通常提供：

~~~text
Get(Request) returns (GetResponse)
Set(Request) returns (SetResponse)
Delete(Request) returns (DeleteResponse)
Invalidate(Request) returns (InvalidateResponse)
~~~

### 5.2 gRPC Client 的职责

gRPC Client 是远程调用的发起方，负责：

- 根据节点地址创建 Channel；
- 使用 Stub 调用远程方法；
- 构造 Request；
- 设置超时和取消；
- 处理 Response；
- 检查 Status；
- 在必要时重试或重新路由。

### 5.3 Service 基类不是 gRPC Server

代码生成后通常会出现一个服务端基类：

~~~text
Cache::Service
~~~

它只是业务方需要继承的接口模板，不是正在监听端口的服务器。

真正的关系是：

~~~text
生成的 Cache::Service 基类
        ↓ 继承
业务 CacheService
        ↓ 注册到
grpc::Server
        ↓ 监听端口
远程 gRPC Client 才能调用
~~~

服务端伪代码：

~~~cpp
class CacheService final : public Cache::Service {
public:
    grpc::Status Get(
        grpc::ServerContext *context,
        const Request *request,
        GetResponse *response) override
    {
        // 校验 request
        // 查询本地缓存
        // 填充 response
        return grpc::Status::OK;
    }
};
~~~

客户端伪代码：

~~~cpp
Request request;
request.set_key("user:42");

GetResponse response;
grpc::Status status = stub->Get(&context, request, &response);
~~~

## 6. Protobuf、.proto 和 gRPC 的关系

### 6.1 .proto 同时描述消息和服务

一份 .proto 文件可以同时描述消息和 RPC：

~~~proto
syntax = "proto3";

package cache;

message Request {
    string group = 1;
    string key = 2;
    bytes value = 3;
}

message GetResponse {
    bytes value = 1;
}

service Cache {
    rpc Get(Request) returns (GetResponse);
}
~~~

其中：

- message 描述请求和响应的数据结构；
- service 描述服务；
- rpc 描述远程方法；
- 字段编号构成协议的一部分。

### 6.2 Protobuf 生成消息代码

使用 protoc 处理 message 后，通常生成：

~~~text
cache.pb.h
cache.pb.cc
~~~

这些代码提供：

- Request 和 Response 类；
- 字段 getter 和 setter；
- SerializeToString；
- ParseFromString；
- Clear、CopyFrom、MergeFrom；
- 描述符和反射信息。

### 6.3 gRPC 插件生成调用代码

使用 gRPC 代码生成插件处理 service 后，通常生成：

~~~text
cache.grpc.pb.h
cache.grpc.pb.cc
~~~

这些代码通常提供：

- 客户端 Stub；
- 服务端 Service 基类；
- RPC 方法绑定；
- 注册和调用所需的辅助代码。

完整关系：

~~~text
.proto
  │
  ├─ protoc
  │    └─ *.pb.h / *.pb.cc
  │         Protobuf 消息类和编解码
  │
  └─ protoc + grpc_cpp_plugin
       └─ *.grpc.pb.h / *.grpc.pb.cc
            gRPC Stub 和 Service 基类
~~~

### 6.4 Protobuf 可以脱离 gRPC

Protobuf 只负责数据描述和编码，可以单独用于：

- 文件；
- 数据库存储；
- 消息队列；
- 自定义 TCP；
- HTTP 请求体；
- 其他 RPC 框架。

同样，gRPC 理论上也可以使用其他序列化方式，但标准 gRPC 项目通常使用 Protobuf，因为它能够同时提供跨语言消息定义和代码生成。

## 7. Protobuf 字段和协议兼容性

字段编号会进入 Protobuf 的 wire format：

~~~proto
message Request {
    string key = 1;
    bytes value = 2;
}
~~~

因此字段编号一旦发布，不应该随意修改。

常见兼容规则：

1. 不修改已经使用过的字段编号；
2. 不复用已经删除的字段编号；
3. 新字段使用新的编号；
4. 新客户端读取旧消息时使用默认值；
5. 旧客户端读取新消息时忽略未知字段；
6. 删除字段后可以用 reserved 保留名称和编号。

这也是为什么 Protobuf 不只是“一个序列化工具”：.proto 文件本身就是跨进程、跨语言的协议契约。

## 8. 节点变化链路

### 8.1 节点加入

~~~text
新节点启动
    ↓
启动 gRPC Server
    ↓
获取自己的 gRPC 地址
    ↓
启动 etcd Client
    ↓
注册地址并绑定 Lease
    ↓
其他 Watch 客户端收到 PUT
    ↓
更新节点列表
    ↓
更新一致性哈希环
~~~

### 8.2 节点宕机

~~~text
节点宕机
    ↓
无法 KeepAlive
    ↓
Lease 过期
    ↓
注册信息失效或被删除
    ↓
Watch 客户端收到 DELETE
    ↓
从本地节点列表移除
    ↓
从一致性哈希环移除
    ↓
后续请求选择其他节点
~~~

### 8.3 请求进行中节点宕机

节点列表更新不能自动挽救已经发出的 RPC。正在进行的 gRPC 请求仍可能遇到：

- 连接断开；
- Deadline Exceeded；
- Unavailable；
- 服务器未找到；
- 响应已经部分发送。

所以 gRPC Client 和路由器还需要定义：

- 超时策略；
- 重试策略；
- 是否重新选择节点；
- Set 是否幂等；
- Delete 是否可以安全重试；
- Invalidate 是否允许丢失或延迟。

服务发现解决“下一次请求找谁”，不等于自动解决“当前请求如何恢复”。

## 9. 写入和节点间同步链路

etcd 主要维护节点拓扑，不负责同步每个缓存 value。

一种常见的写入流程是：

~~~text
客户端
    ↓
一致性哈希选择主节点
    ↓
gRPC Client 调用主节点 Set
    ↓
主节点更新本地缓存
    ↓
通过 gRPC Client 通知其他节点 Invalidate
~~~

删除流程可能是：

~~~text
客户端或协调节点
    ↓
通过 gRPC 调用多个缓存节点
    ↓
各节点删除本地副本
~~~

这条链路中各组件的角色是：

~~~text
etcd
    提供节点地址

一致性哈希
    选择节点

Protobuf
    编码 Set、Delete、Invalidate 的请求

gRPC Client
    发起远程调用

gRPC Server
    接收远程调用

本地缓存
    执行真正的数据变更
~~~

## 10. etcd 的 gRPC 与缓存系统的 gRPC

这是一个非常容易混淆的地方。

etcd v3 的 API 本身也可以通过 gRPC 访问，因此系统中可能存在两类完全不同的 gRPC 调用：

### 10.1 控制平面 gRPC

~~~text
etcd Client
    ↓
etcd Server
~~~

调用内容可能是：

~~~text
Put
Get
Watch
LeaseGrant
LeaseKeepAlive
~~~

### 10.2 数据平面 gRPC

~~~text
缓存节点 A 的 gRPC Client
    ↓
缓存节点 B 的 gRPC Server
~~~

调用内容可能是：

~~~text
Get
Set
Delete
Invalidate
~~~

两者虽然都可能使用 gRPC 技术，但它们的：

- 服务地址不同；
- .proto 定义不同；
- 服务名称不同；
- 数据含义不同；
- 生命周期不同；
- 故障处理不同。

可以把它们记成：

~~~text
etcd gRPC：管理“节点地图”
缓存 gRPC：执行“缓存操作”
~~~

## 11. 组件职责总表

| 组件 | 所在位置 | 主要职责 | 不负责什么 |
| --- | --- | --- | --- |
| etcd Server | 独立基础设施 | 保存节点注册、Lease、Watch 和配置 | 不负责缓存 LRU 和缓存业务 |
| etcd Client | 应用进程内部 | 注册、续租、Watch、读取节点列表 | 不负责执行缓存 Get |
| 一致性哈希 | 路由模块内部 | 根据 key 选择节点 | 不负责建立网络连接 |
| .proto | 协议定义文件 | 描述消息和 RPC 契约 | 不包含业务实现 |
| Protobuf | 编解码和生成代码 | 定义消息、序列化、反序列化 | 不负责连接和远程调用 |
| protoc | 构建工具 | 生成 Protobuf 消息代码 | 不负责运行时通信 |
| grpc_cpp_plugin | 构建工具 | 生成 Stub 和 Service 基类 | 不负责业务逻辑 |
| gRPC Client | 调用方进程内部 | 发起 RPC、处理超时和状态 | 不负责本地缓存实现 |
| gRPC Server | 被调用方进程内部 | 监听端口、接收 RPC、返回响应 | 不负责全局服务发现 |
| Service 实现 | gRPC Server 内部 | 把 RPC 转换成本地业务调用 | 不等于运行时 Server |
| HTTP/2 | 网络传输层 | 承载标准 gRPC 通信 | 不负责业务协议定义 |
| CacheGroup / LRU | 缓存节点内部 | 保存数据、读取数据、淘汰数据 | 不负责节点发现 |

---

## 12. 常见错误理解

### 12.1 etcd 是缓存数据库

不准确。etcd 更适合保存节点注册和配置等元数据，缓存 value 应由缓存节点管理。

### 12.2 etcd Client 就是缓存 gRPC Client

不准确：

~~~text
etcd Client → etcd Server
gRPC Client → 缓存 gRPC Server
~~~

它们连接的服务、调用的 API 和所在的系统平面都不同。

### 12.3 gRPC Server 就是 Service 基类

不准确。Service 基类是生成代码提供的接口模板，grpc::Server 才是负责监听端口和接收网络调用的运行时对象。

### 12.4 Protobuf 负责网络通信

不准确。Protobuf 负责定义和编码数据，gRPC、HTTP、TCP 或消息队列都可以使用 Protobuf。

### 12.5 有了 .proto 就自动有 gRPC 服务

不一定。只有 message 定义时，protoc 只能生成消息类。要生成 Stub 和 Service，还需要 service 定义以及 gRPC 代码生成插件。

### 12.6 etcd 参与每一次缓存请求

通常不应该这样设计。etcd Client 应该把节点信息同步到本地，缓存请求直接使用本地路由并通过 gRPC 访问目标节点。

### 12.7 节点下线后 Watch 就能自动恢复所有请求

不准确。Watch 只能更新未来请求的节点列表。已经发出的 gRPC 请求仍需要超时、错误处理、重试和幂等性设计。

## 13. 最终记忆方式

把整个系统压缩成一句话：

> etcd Client 从 etcd Server 得到节点地图，一致性哈希根据 key 选择目的地，gRPC Client 发起远程调用，Protobuf 搬运结构化数据，gRPC Server 把调用交给本地缓存业务。

再压缩成一条链：

~~~text
etcd Server
    ↓
etcd Client
    ↓
节点列表和一致性哈希
    ↓
gRPC Client
    ↓
Protobuf 序列化
    ↓
HTTP/2 + gRPC
    ↓
gRPC Server
    ↓
Protobuf 反序列化
    ↓
Service 实现
    ↓
CacheGroup / LRU
~~~

这条链路就是分布式缓存中控制平面、数据平面、协议定义、网络通信和本地缓存逻辑的完整关系。
