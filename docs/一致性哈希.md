# 一致性哈希基础

## 1. 为什么分布式缓存需要分片

单台缓存服务器同时受到容量和吞吐量限制：数据可能超过单机内存，请求量也可能超过单机处理能力。因此，缓存系统通常会部署多个节点，并把 key 分配到不同节点上。

分布式缓存首先要解决的问题是：

> 给定一个 key，客户端如何稳定地找到负责它的缓存节点？

这个过程称为数据分片（sharding），可以抽象为：

```text
key -> 某个缓存节点
```

映射必须稳定。否则，写入时去了节点 B，读取时却随机访问节点 C，就会产生不必要的缓存未命中。

## 2. 普通取模哈希的问题

最直接的分片方式是根据 key 的哈希值取模：

```text
nodeIndex = hash(key) % nodeCount
```

例如有 3 个节点：

```text
hash(user:1001) = 10  -> 10 % 3 = 1 -> Redis 1
hash(user:1002) = 17  -> 17 % 3 = 2 -> Redis 2
hash(product:2001) = 24 -> 24 % 3 = 0 -> Redis 0
```

在节点数量不变时，这种方式简单、快速，而且分布通常比较均匀。

但节点数量一旦变化，取模基数也会变化。例如从 3 个节点扩容到 4 个节点：

```text
原来：hash(key) % 3
现在：hash(key) % 4
```

同一个 key 的结果可能完全不同：

```text
10 % 3 = 1
10 % 4 = 2
```

这意味着大量 key 都会被映射到新节点。缓存中的旧数据仍在原节点，而客户端按新规则去其他节点读取，导致大量缓存未命中；如果请求回源数据库并重新写入缓存，还可能造成数据库压力瞬间升高。

节点减少时也会发生类似问题。因此，普通取模哈希的主要缺点不是查询慢，而是节点集合变化时会引发大范围的映射变化和数据迁移。

## 3. 一致性哈希的核心思想

一致性哈希不把节点数量直接放进 key 的计算公式，而是把节点和 key 放入同一个固定的哈希空间：

1. 对每个缓存节点的标识（例如节点名或地址）做哈希，得到节点位置。
2. 对每个 key 做哈希，得到 key 的位置。
3. 根据固定方向寻找 key 遇到的第一个节点，该节点负责这个 key。

为了说明方便，可以先把哈希空间画成从 `0` 到 `100` 的直线：

```text
0------A----------B----------C------100
       20         50         80
```

假设：

```text
hash(A) = 20
hash(B) = 50
hash(C) = 80

hash(user1) = 10
hash(user2) = 30
hash(user3) = 70
hash(user4) = 90
```

规定 key 沿顺时针方向（在线性示意图中即向右）寻找第一个节点：

```text
user1 = 10 -> A = 20
user2 = 30 -> B = 50
user3 = 70 -> C = 80
user4 = 90 -> 回到 A = 20
```

因此，各节点负责的是它前一个节点到自身之间的那段哈希区间。实现中也可以采用相反方向，只要所有客户端使用同一种规则即可。

## 4. 为什么要组成哈希环

线性哈希空间存在边界问题：如果 key 的哈希值位于最后一个节点之后，就找不到右侧节点。

因此，把最大值和最小值连接起来，形成环：

```text
0 -> 1 -> 2 -> ... -> 最大值
^                         |
|_________________________|
```

例如节点位置为 `A=20`、`B=50`、`C=80`，哈希值为 `95` 的 key 沿顺时针方向继续查找，会越过最大值并回到 `0`，最终找到 `A`。

“环”主要用于处理哈希空间的首尾边界；一致性哈希真正重要的性质是节点增删时只影响局部映射。

## 5. 节点变化时为什么只影响局部 key

在原有节点中插入 `D`，并假设：

```text
hash(D) = 40
```

哈希环从：

```text
0------A----------B----------C------
       20         50         80
```

变为：

```text
0------A-----D----B----------C------
       20    40   50         80
```

原本位于 `A` 和 `B` 之间的 key 会先遇到 `D`，所以其中一部分从 `B` 改由 `D` 负责；其他区间的第一个节点没有变化，key 的映射也不变。

删除一个节点时，该节点负责的区间会交给环上的下一个节点，同样只影响相邻的一段 key。

所以一致性哈希的目标可以概括为：

> 节点集合变化时，让尽可能少的 key 改变负责节点。

这可以减少缓存失效、数据迁移和对后端数据库的冲击。它并不保证“完全没有 key 变化”，也不意味着数据会自动从旧节点搬到新节点；实际迁移和回源策略仍需要由缓存系统负责。

## 6. 与普通取模哈希的对比

| 方面 | 普通取模哈希 | 一致性哈希 |
| --- | --- | --- |
| 映射依据 | `hash(key) % 节点数量` | key 在固定哈希空间中的位置及其后继节点 |
| 节点数量变化 | 取模基数改变，大量 key 可能改变映射 | 通常只影响新增/删除节点附近的区间 |
| 实现复杂度 | 低 | 需要维护节点位置并查找后继节点 |
| 主要风险 | 扩缩容导致大量缓存失效 | 节点分布不均可能导致负载不均 |

## 7. “一致性”不等于缓存与数据库一致

一致性哈希中的“一致性”，指的是节点集合变化时，key 到节点的映射尽量保持稳定。

它和下面这些问题不是同一个概念：

- Redis 与 MySQL 的数据一致性；
- 缓存更新、删除和过期策略；
- 主从复制或多副本之间的一致性。

一致性哈希只解决“这个 key 应该由哪个节点负责，以及节点变化时如何减少映射扰动”这一类问题。

## 8. 虚拟节点：解决环上的数据倾斜

基础的一致性哈希把每台物理服务器只放在环上的一个位置。由于哈希结果具有随机性，少量节点可能分布得很不均匀。

例如：

```text
A = 10，B = 20，C = 80
```

按照顺时针寻找后继节点的规则，三个节点大致负责：

```text
C -> A：80 ~ 100 以及 0 ~ 10
A -> B：10 ~ 20
B -> C：20 ~ 80
```

如果 key 的哈希值分布均匀，C 可能需要负责约 60% 的哈希空间，而 B 只负责约 10%。即使三台机器配置完全相同，也会出现：

```text
C：负载过高
B：资源闲置
```

这种现象称为数据倾斜（data skew）或负载不均衡。

### 8.1 虚拟节点是什么

虚拟节点（Virtual Node，简称 vnode）是物理节点在哈希环上的多个逻辑身份。它们不是真正的服务器，也不独立存储数据，而是用于把物理节点负责的区域拆成多个小区间。

例如：

```text
Cache A -> A#1, A#2, A#3, A#4
Cache B -> B#1, B#2, B#3, B#4
Cache C -> C#1, C#2, C#3, C#4
```

对每个 vnode 单独哈希，并将它们分散到环上：

```text
A#1 -> 5     B#1 -> 12    C#1 -> 20
A#2 -> 31    C#2 -> 40    B#2 -> 48
C#3 -> 60    A#3 -> 72    B#3 -> 83
A#4 -> 90    C#4 -> 95    B#4 -> 99
```

此时物理节点在环上的分布类似：

```text
A B C A C B C A B A C B
```

key 的路由过程也多了一层映射：

```text
key
 ↓
hash(key)
 ↓
找到顺时针方向的第一个 vnode
 ↓
通过 vnode 找到所属的物理节点
 ↓
访问物理节点
```

例如 `hash(user:1001) = 68`，顺时针找到 `A#3 = 72`，最终访问的仍然是 Cache A：

```text
user:1001 -> A#3 -> Cache A
```

### 8.2 为什么虚拟节点能改善均衡

如果每台机器只有一个位置，少量随机点之间的间隔可能差异很大；如果每台机器拥有很多 vnode，所有 vnode 会更密集地散布在整个环上。

假设有 3 台物理机器，每台有 100 个 vnode：

```text
环上总共有 300 个位置
A、B、C 各有约 100 个位置
```

每台机器负责的是许多分散的小区间。这些小区间的总长度通常会更接近，因此在 key 哈希均匀的前提下，三台机器的分配比例也更接近：

```text
A ≈ 1/3，B ≈ 1/3，C ≈ 1/3
```

虚拟节点数量越多，分布通常越平滑，但收益会逐渐递减，同时会增加环的维护成本和路由元数据。实际数量应根据节点规模、负载波动和实现开销进行选择。

### 8.3 节点故障时的负载转移

虚拟节点还可以把故障影响拆散。

没有虚拟节点时，物理节点 B 只有一个位置。B 故障后，它负责的整个区间通常会交给顺时针方向的下一个节点，例如 C：

```text
B 的全部区间 -> C
```

这样 C 需要一次性承接 B 的全部数据和请求，容易造成二次过载。

使用虚拟节点时，B 的多个 vnode 分散在环上：

```text
B#1、B#2、B#3、...
```

B 故障后，删除这些 vnode；每个 vnode 原来负责的区间分别交给各自的后继 vnode。因此，B 的负载可能分散给 A、C 以及其他节点，而不是集中转移给单个节点。

同理，新增一个物理节点时，它的多个 vnode 会从原有节点分别“截取”许多小区间，迁移范围被拆得更细，数据和请求的转移通常也更平滑。

### 8.4 按能力设置权重

虚拟节点数量不必对所有物理节点相同，因此可以支持加权分片。例如：

```text
Cache A：32 GB  -> 100 个 vnode
Cache B：32 GB  -> 100 个 vnode
Cache C：64 GB  -> 200 个 vnode
```

在其他条件相近时，C 大致承担两倍于 A 或 B 的哈希空间：

```text
A ≈ 25%，B ≈ 25%，C ≈ 50%
```

这是一种近似的加权负载均衡。权重应同时考虑内存、CPU、网络带宽和实际请求能力，而不能只看磁盘或内存容量。

### 8.5 实现时需要维护什么

一个典型实现至少需要维护两类信息：

```text
有序 vnode 环：vnode 哈希值 -> vnode 标识
映射表：vnode 标识 -> 物理节点地址
```

路由步骤通常是：

1. 对 key 做哈希。
2. 在按哈希值排序的 vnode 列表中，查找第一个不小于该哈希值的位置（`lower_bound`）。
3. 如果已到列表末尾，则回到列表开头，实现环形查找。
4. 通过映射表得到物理节点地址。

新增或删除物理节点时，需要批量新增或删除它对应的 vnode，并让客户端或路由服务使用同一份节点配置。vnode 的命名和哈希算法也必须稳定，否则重启或不同客户端之间可能得到不同的环布局。

### 8.6 虚拟节点能解决和不能解决的问题

虚拟节点主要改善的是“节点在哈希空间中的分布不均”：

| 问题 | 虚拟节点的作用 |
| --- | --- |
| 节点位置偶然聚集 | 用多个分散位置降低倾斜 |
| 新增节点 | 将迁移拆成多个局部区间 |
| 节点故障 | 将故障节点的负载分散给多个后继节点 |
| 节点配置不同 | 通过不同 vnode 数量实现近似权重 |
| 单个热点 key 访问量过高 | 不能直接解决，需要副本、热点隔离或其他策略 |

因此，虚拟节点不是真正增加服务器，也不能替代缓存高可用、数据迁移、热点 key 保护等机制。它建立在 key 哈希分布较均匀的前提上；如果业务本身存在少数超高频 key，还需要额外的热点治理方案。

## 9. 一条完整的理解路径

```text
单机容量或吞吐量不足
        ↓
部署多个缓存节点
        ↓
需要把 key 稳定分配到节点
        ↓
普通方案：hash(key) % 节点数量
        ↓
扩缩容导致节点数量变化
        ↓
大量 key 映射改变，缓存大面积未命中
        ↓
一致性哈希：节点和 key 共同映射到固定哈希环
        ↓
key 找顺时针方向的第一个节点
        ↓
节点增删时只调整相邻的一小段 key
        ↓
普通一致性哈希可能出现节点位置不均
        ↓
虚拟节点让一台物理服务器对应多个环上位置
        ↓
数据倾斜和故障转移更加均匀
        ↓
还能支持不同权重的服务器
```

一句话记忆：

> 一致性哈希是一种为分布式缓存分配“哈希空间地盘”的方法：节点和 key 位于同一个哈希环上，节点变化时只重新分配附近的一小段 key，而不是让所有 key 重新洗牌。

> 虚拟节点则是让一台真实服务器在环上拥有多个逻辑位置，把它负责的区域拆成许多小块，从而改善数据分布、故障转移和不同规格节点之间的负载分配。
